### `LoopPlugin`: what the conflict was

Upstream `1aee2124da` made `runningModeRecord()` a **pure read** (`getRunningModeActiveAt(now)`)
and gave reconciliation its own trigger: `EventPumpStatusChanged` plus the start of `invoke()`,
both calling `runningModePreCheck()`. The fork had it the other way round - every reader called the
pre-check first, which made ~36 readers writers and wrote a `Pump suspended` row each time. The
fork also carried a `runningModeSnapshot` (`AtomicReference`) that the pre-check refreshed but
nothing ever read.

Resolution:

- `runningModeRecord()` is upstream's pure read.
- `runningModePreCheck() = reconcileMutex.withLock { reconcileRunningMode() }`, with the body a
  `while (true)` loop (the `Mutex` is not reentrant, so the old recursion would deadlock).
- The fork's pump guards are re-applied inside it: `runCatching { activePlugin.activePumpInternal }`
  early return (config builder with no pump yet), the
  `isInitialized() && isConnected() && !isConnecting() && !isHandshakeInProgress()` gate,
  `pump.isSuspendedForRunningModeReconciliation()` (Medtrum narrows it to
  `pumpState.isSuspendedByPump()`), `allowedNextModesWhenSuspendedByPump()` and
  `endPumpSuspendedRunningMode()`.
- The fork's `runningModeSnapshot` machinery, its RM `observeChanges` collector and
  `runningModePreCheckSuspend()` are gone (dead code: written, never read).

The merged `LoopPluginTest` (both sides auto-merged) pins both halves: "reading the running mode
never writes", "two reconciliations arriving together write only one row", and the fork's
suspend/resume reconciliation.

**ASYNC IMPACT**: reconciliation runs under `reconcileMutex` and is triggered from the
`EventPumpStatusChanged` collector and from the start of `invoke()`. Two triggers can now arrive
together; the mutex serialises them and the loser re-reads the mode inside the loop instead of
acting on a stale one. The loop replaces the old recursion on purpose - `Mutex` is not reentrant,
so recursing would deadlock the loop.
