### What the restored tests found

None of it was merge damage. In every case below the test and the code it exercises are byte
identical to the fork tip (`git diff HEAD:<old path> <new path>` is empty), so the test was already
stale or already flaky before the merge - the flip just stopped it from running.

1. **API drift, not behaviour: `R.string` literals in host tests.** Four tests in `:ui`,
   `:plugins:main` and `:plugins:aps` compared `R.string.xyz` ids against code that now passes a
   `TextRef`. Converted to the generated strings objects (`UiStrings`, `CoreUiStrings`,
   `ApsStrings`). Two harness notes come out of this, worth keeping:
   - `gs(TextRef)` / `gs(Int)` with no argument is a **different Java method** from
     `gs(TextRef, vararg Any?)` / `gs(Int, vararg Any?)`. A stub for the vararg form does not
     cover a call without arguments, and the other way round.
   - The whole Kotlin `vararg` array is **one** Mockito argument: stub it with `anyVararg()`.
     Two separate `any()` matchers never match. An untyped `any()` on the overloaded `gs` also
     fails to infer the parameter type, so write `any<TextRef>()` or `any<Int>()`.
   - `UserEntryLogger.log(...)` leaves a defaulted `note` out of the call site, so a `verify`
     that names the other three arguments needs `note = any<String>()` as well, or Kotlin fills
     the default and Mockito counts one raw value among the matchers.
2. **`LegacyPrebolusLatchTest`** pinned the old lock window `runtime × 60 s + 90 s`. Production
   deliberately replaced it with a fixed 30 min + 90 s window, because an early-firing tag unlocked
   in the middle of the meal window and fired twice. The test now pins the fixed window on both
   sides of the boundary (at the end: allowed, one millisecond inside: blocked).
3. **`AimiControlCenterSnapshotTest`** expected the top meal label. The two prebolus keys accept up
   to 20 U now, and the projection normalises against the key's own range, so a 5 U / 1.5 U stack
   scores about 0.74 - index 3, not 4 - and the wider spread lowers the confidence to 0.53. Both
   expectations updated with the reason. **The scoring itself is unchanged by the merge**, so this
   is a fork-side question: with the current ranges the Control Center reads more conservative than
   the settings are. See the follow-ups.
4. **`BoostV5AutoConfigTest`** locks the list of auto-configured double keys. `ApsBoostV5PrimerCapU`
   joined that list after the test was written; added.
5. **Two classes raced a background refresh.** `KalmanFilterTest` and
   `DetermineBasalInvocationCachesTest` both read values that a coroutine on `Dispatchers.IO` writes:
   - `KalmanISFCalculator` warms a TDD cache in the background and reads the preference until it
     lands. With a relaxed mock the refresh stores 0.0, so on a fast machine the calculator saw an
     unusable TDD and returned 223 mg/dL/U where the test expected the 15.0 floor - the same test
     passed or failed with the speed of the host. The mock now answers the same TDD on both paths.
   - `DetermineBasalInvocationCaches` publishes from a background coroutine, and the first read of
     an invocation fills that invocation's slot whether or not the value has arrived. The tests now
     park the calculator on a `CountDownLatch`, so "nothing is ready yet" is deterministic, and they
     wait across invocations for the published value.

### Unit tests: what the suite found

Three real failures, all fixed. One was the merge's own fault; the other two were already red before
it.

**1. Merge regression — `WearApp` lost `injectMetroMembers(this)`.** The conflict kept the fork's
`onCreate` body (the fork's `cwfComplicationUpdater.start()` and the preference listener held in a
field so it is not collected) and dropped upstream's injection call, which was the first line of that
body. Android builds the Application object itself, so nothing else fills its `@Inject` fields:
`exceptionHandlerWear` stayed unset and `onCreate` threw `UninitializedPropertyAccessException`. On a
watch the app would have crashed on launch. In the suite it showed as **150 failures across 34 wear
test classes** - every Robolectric test that builds the application fails before reaching its own
code, which is what pointed at the application class. The call is restored as the first line of
`onCreate`. A sweep of **every** file where upstream calls `injectMetroMembers` against the working
tree finds no other dropped call; the sweep is now a checklist item.

**2. Pre-existing fork bug — the wear tile tests never learned about `afrezza`.**
`ActionSource.getActions()` returns the fork's `afrezza` action between `bolus` and `carbs` (upstream
has no such action), but the two upstream tests still stubbed only the ten original strings and still
asserted seven actions. The unstubbed `getString` returned null, so every test that called
`getActions()` died with an NPE at `ActionSource.kt:51`, and the assertions behind it were stale as
well (7 vs 8 actions, first-four fallback, icon list). Both test files are unchanged by this merge
(`git diff --cached --stat` prints nothing for them) and the `afrezza` action is already in
`ActionSource` at the pre-merge tag, so they were red before it too. Fixed the tests, not the
production list: two stubs added, action count and order updated, the unused `orderedSettingNames`
property removed.

**3. Pre-existing fork bug - the Medtrum bolus type fallback was never tested.**
`GetRecordPacket` records a bolus that the pump reports back, and when the in-memory
`DetailedBolusInfo` has already expired it now passes `medtrumPump.bolusOriginalType` instead of
`type = null`, so an AAPS-initiated bolus keeps its real type (SMB, for example). That change came
with the fork commit `3010160f2f` (2026-07-27) and it touched **only** the production file; the test
kept asserting `type = null` and the default `bolusOriginalType` is `NORMAL`, so
`handleResponseGivenBolusRecordWhenAndNoDetailedBolusInfoPresentThenExpectPumpSyncWithPumpId` has
been red since that day. The tests could not run at all between the flip and this merge, and the
dependency failure below hid it in the first sweep, so it only showed up in the full Android run.
Fixed the test, not the production line, to keep the fork feature: the test writes
`bolusOriginalType = BS.Type.SMB` before the call and checks that SMB arrives at
`syncBolusWithPumpId`, so it now proves the fallback carries the type across instead of only
matching the default.
